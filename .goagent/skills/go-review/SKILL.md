# Go 代码审查

按以下步骤审查，**只读不改**，除非用户明确要求修复。

## 1. 确定范围

- 用户指定了文件或目录就只看这些；否则用 `bash` 运行 `git diff --stat` 与 `git diff` 找出改动。
- 先运行 `go vet ./...` 与 `go build ./...`，记录编译器与 vet 发现的问题。

## 2. 逐项检查

**正确性**
- 边界条件：空切片、nil map 写入、越界、整数溢出、除零。
- 字符串按字节截断是否会切开 UTF-8 字符。
- `defer` 在循环中使用、`defer` 中忽略的错误（如 `f.Close()` 之于写文件）。

**错误处理**
- 是否吞掉了错误（`_ =`、空的 `if err != nil {}`）。
- 包装错误用 `fmt.Errorf("...: %w", err)`，判断用 `errors.Is/As`，不要比较字符串。
- 错误信息是否包含足够上下文（哪个文件、哪个 ID）。

**并发安全**
- 共享变量是否有锁或原子操作；`sync.WaitGroup.Add` 是否在 goroutine 外调用。
- goroutine 是否可能泄漏（无人接收的 channel、没有退出条件的循环）。
- 是否正确传递和响应 `context.Context` 的取消。
- 建议用 `go test -race` 验证。

**API 与可读性**
- 导出的标识符是否有文档注释；命名是否符合 Go 惯例（缩写全大写如 `ID`、`URL`）。
- 函数是否过长、参数是否过多；接口是否定义在使用方。
- 是否引入了不必要的第三方依赖。

**测试**
- 改动是否有对应测试；是否使用表驱动；失败信息是否清楚说明"得到什么、期望什么"。

## 3. 输出格式

按严重程度分组，每条给出 `文件:行号`、问题、原因与修改建议：

```
## 必须修复
- tool/fs.go:42 —— 截断 line[:2000] 可能切开 UTF-8 字符。建议回退到字符边界。

## 建议改进
- ...

## 做得好的地方
- ...
```

最后用一句话给出总体结论（可以合并 / 修改后合并 / 需要重新设计）。
